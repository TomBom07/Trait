# Trait v1 compatibility

Trait 1.0 defines a stable first compatibility boundary for behavior contracts and project state.

## Stable in v1

### Behavior contract schema

`schemaVersion: 1` packages use:

- package identity: `name`, `version`, `summary`, and `intent`;
- behavior: `rules`, `invariants`, optional `security`, and `acceptance`;
- optional implementation guidance;
- optional host verification scripts;
- optional deterministic `project-script` acceptance graders;
- optional trait requirements, conflicts, provided capabilities, and required capabilities.

Rule and acceptance IDs are part of a contract's public behavior identity. Rewording should keep an ID when its meaning is unchanged.

### Lock and evidence state

`.trait/lock.json` version 1 records the exact contract version, source, checksum, agent, relation metadata, and latest successful verification.

Evidence receipts are durable and inspectable. Model-backed file evidence carries content hashes so source drift can be detected. Deterministic graders are rerun by checks-only verification.

### Registry protocol

Registry format v1 uses:

- a non-authoritative `v1/index.json` discovery catalog;
- exact-version descriptors;
- SHA-256 content-addressed artifacts;
- Ed25519 publisher signatures;
- explicit fingerprint trust;
- local revocation and cache state;
- exact artifact hashes in registry-backed lock sources.

A registry catalog can suggest a package, but it can never make an artifact trusted.

### Network boundary

Normal `trait add`, `update`, `remove`, `verify`, `list`, and `order` operations do not implicitly download a remote Trait package.

Remote package network access remains explicit through registry discovery, inspection, trust, and fetch commands.

## Compatibility policy

Within the 1.x line:

- existing schema-version-1 contracts should continue to load unless they relied on behavior documented as invalid or unsafe;
- existing lock-version-1 state should remain readable;
- registry v1 artifacts remain content-addressed and signature-verifiable;
- new optional fields may be added without changing existing contract meaning;
- breaking package-format or state-format changes require a new format version.

The coding-agent adapter interface is currently an internal implementation boundary rather than a separately versioned public JavaScript API.

## Deliberate limits

Trait 1.0 does not claim formal verification or exactly-once distributed execution. Model-assisted evidence remains evidence, not proof.

Trait also does not automatically download dependency graphs or operate a central hosted registry. Registries can be hosted as static HTTPS content, and dependency ordering is explicit.

Codex is the first built-in coding-agent adapter. Additional adapters can be added without changing the behavior package format.
