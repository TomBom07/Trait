Use the host application's existing persistence, event, request-context, and authorization conventions.

Define a narrow structured audit event rather than dumping request bodies or arbitrary objects. Prefer stable action names and target identifiers that can be queried later. Capture correlation or trace context already generated by the application when available.

Do not log secrets and do not rely on a post-hoc regex scrubber as the primary defense. Build an allowlist of audit fields from trusted server-side values.

Choose and document failure semantics. Some applications can enqueue audit delivery asynchronously after a committed domain change; others require the audit write to participate in the same transaction or fail closed. The implementation should reflect the host's actual assurance requirement.

Tests should assert the event contents, a failure outcome, redaction of representative sensitive values, and access control for any audit-reading surface.
